# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

Find and analyse the machine code that is hot in JVM programs. The repo will hold two parts:

1. **A JVMTI agent** that runs inside the target JVM. It captures JIT-compiled code and samples program counters.
2. **Analysis tools** that take what the agent captured and examine the structure of the machine code alongside the PC samples, so hot instructions and regions can be attributed and understood.

The target architectures are **x86-64** and **AArch64**. Keep architecture-specific code (decoding, instruction semantics, register naming) separate from architecture-neutral code, so other ISAs can be added later.

## Build

Gradle (Kotlin DSL) via the wrapper. All Java code compiles with `--release 17` (the oldest supported runtime) using whichever JDK runs Gradle, 17 or newer, so don't use APIs newer than Java 17 (e.g. `List.getFirst()`). JNI/JVMTI headers also come from that JDK.

- `./gradlew build` — build everything and run all tests
- `./gradlew :parse:test` / `./gradlew :agent-test:test` — one module's tests
- `./gradlew :parse:test --tests 'instructive.parse.ParseTest.loads'` — a single test
- `scripts/test-linux.sh [all|amd64|arm64] [gradle tasks...]` — run the build, by default `build` (all tests), in Linux containers for x86-64 and/or AArch64, using `docker/linux-build.Dockerfile`.
  - **Variants:** `DISTRO=ubuntu|alpine` picks glibc (Ubuntu 22.04 with Temurin) or musl (Alpine 3.23 with Alpine's OpenJDK, since Temurin has no Alpine JDK 17 for aarch64), and `JDK=17|21|25` picks the JDK; `OUT=dir` collects the built `.so` and `REPORTS=dir` the test reports. CI runs exactly this script. The checkout is mounted read-only and copied inside (by `scripts/linux-build-in-container.sh`) without its build outputs, so host and Linux builds don't mix; Gradle caches live in per-arch Docker volumes.
  - **Emulation:** on Apple Silicon, `amd64` runs emulated. It still exercises the x86-64 code paths (PC extraction, `PC_SHIFT` 0), but ThreadSanitizer can't run there. The 4 aarch64-only tests (disassembly and formatter) are skipped on amd64.
  - **PATH:** Docker Desktop's CLI may not be on PATH; the script adds `~/.docker/bin`.
- `./gradlew :agent:nativeLibs` — build the host's native library into `agent/build/native-libs/META-INF/native-libs/<os>-<arch>/`
- `./gradlew :agent:jvmJar -Pinstructive.nativeLibs=dir1,dir2` (add `-Pinstructive.buildNative=false` to leave out the host's own library) — build the agent jar, merging in native libraries built elsewhere (each dir contains `META-INF/native-libs/<os>-<arch>/...`)

## CI

`.github/workflows/ci.yml`, three stages:
1. **`parse-and-analyse`:** `:parse:test :analyse:test` on JDK 25. It is quick, and gates the rest.
2. **`agent-test` matrix:** `:agent-test:test` for {ubuntu, alpine} × JDK {17, 21, 25} × {amd64, arm64}, on native `ubuntu-24.04`/`ubuntu-24.04-arm` runners via `scripts/test-linux.sh`. Each distro/arch's JDK 17 job uploads its `.so` as `native-<distro>-<arch>`.
3. **`package`:** builds the agent jar with JDK 17 from those artifacts only (`-Pinstructive.buildNative=false`), checks the four `linux[-musl]-{x86_64,aarch64}` libraries are present and no `.dylib` is, and uploads `agent-jar`.

macOS isn't built in CI and `.dylib`s aren't published; macOS users build locally.

## Modules

- **agent** — the agent. C++ in `src/main/cpp` (Gradle `cpp-library`, shared linkage, JNI/JVMTI headers taken from the JDK running Gradle) and Java in `src/main/java`. Because `cpp-library` and the `java` plugin both create an `implementation` configuration and can't coexist, the Java code is built by a source set named `jvm` on `java-base`, packaged by the `jvmJar` task and exposed to other projects through the `agentJar` configuration.
  - The native library is **not** a classic `-agentpath` JVMTI agent: never add `Agent_OnLoad`/`Agent_OnAttach`. `NativeLibraryLoader` extracts `META-INF/native-libs/<os>-<arch>/<System.mapLibraryName("instructive")>` from the jar and `System.load`s it. It is called either by a Java program directly or by the Java agent `InstructiveAgent` (set as `Premain-Class`/`Agent-Class`).
  - The native sampler (`instructive::Sampler`, `src/main/headers` + `src/main/cpp`) is created in `JNI_OnLoad`, which obtains the `jvmtiEnv`, and destroyed in `JNI_OnUnload`. Sampling is controlled explicitly through the Java API `instructive.agent.Sampler` (`start()`, `stop()`, `isRunning()`, `kindCounts()`, `forEachMethod()`, `forEachHottestMethod(k, consumer)`, `resetCounts()`). Its private `*0` natives map to `Sampler::start/stop/running`, which are idempotent and return whether the state changed. The JVM only calls `JNI_OnUnload` when the class loader that loaded the library is garbage collected, and the library is currently loaded by the system class loader, so it is never unloaded. Loading it through an isolated class loader so it can be unloaded is planned for later.
  - CPU time sampling is in `CpuTimer` (`cpu_timer.h`/`cpu_timer.cpp`), kept separate from `Sampler`. Per-OS code sits in the same file behind `#if defined(__linux__)`/`__APPLE__`. Both deliver `SIGPROF` every 10ms of CPU time (hardcoded), and `Sampler::start/stop` start and stop the timer.
    - **Linux:** one timer per thread. Each is a `timer_create` on that thread's CPU clock (built from the tid like glibc's `MAKE_THREAD_CPUCLOCK`) with `SIGEV_THREAD_ID`, so the signal interrupts the thread that used the CPU. `start()` covers threads listed in `/proc/self/task`; threads started later get a timer from JVMTI `ThreadStart` (`CpuTimer::thread_started`, which runs on the new thread) and lose it in `ThreadEnd`. Native threads started after `start()` aren't sampled until the next `start()`. The tid → timer map is guarded by a mutex that the signal handler never touches. It is tested in Docker (see Build).
    - **macOS:** no per-thread interval timers exist, so it keeps one process-wide `setitimer(ITIMER_PROF)`, and the thread hooks do nothing.
  - **The `SIGPROF` handler (`signo, siginfo_t*, ucontext`) does not chain to previously registered handlers.** Other sources of SIGPROF may exist, and their signals aren't ours to interpret.
    - **Linux:** every timer labels its signals with `sigev_value.sival_ptr = &own_signal_tag`. The handler ignores any SIGPROF unless `si_code == SI_TIMER` and `si_value` carries that tag.
    - **macOS:** `setitimer` signals carry no value, so any SIGPROF received while started counts as ours.
    - **Installation:** the previous handler is saved only so it can be restored on destruction, if ours is still current. Our handler stays installed across stop/start. Code in the handler must be async-signal-safe and must preserve `errno`.
  - **Never read the code heap or method metadata from the signal handler.** That is what crashes async-profiler-style profilers in production, because nmethods and their metadata are changed and freed underneath a handler. Instead:
    - **Event side:** JVMTI `CompiledMethodLoad`/`CompiledMethodUnload` (enabled in the `Sampler` constructor, with `GenerateEvents` replaying existing nmethods) maintain `CompiledMethodMap`. Each entry is a `CompiledMethod` record holding the name, the code range, and the compile level and id. Those callbacks run on ordinary threads, which is the one place `CodeCache::lookup` is used: the nmethod is live while its load event is posted, so the lookup can supply the level, the id and the full blob range, none of which JVMTI reports.
    - **Signal handler:** `Sampler::on_tick` takes the PC from the ucontext (`ucontext_pc.h`), looks it up in the map and increments the record's atomic `count`. A PC that isn't in the map goes to `CodeCache::classify`, which only compares against bounds fixed at startup.
    - **What stays:** `CodeCache::lookup`/`method_name` are kept for uses off the signal path, such as the JVMTI load callback and `InstructionProfile.machineCode()`.
  - **CompiledMethodMap** (`compiled_method_map.h/.cpp`) is a concurrent radix tree laid out like a page table, keyed by `address >> log2(code heap segment size)`.
    - **Keying and cost:** no two blobs share a segment, so each leaf slot maps to at most one method. Lookup is a fixed number of acquire loads. Insert writes one slot per segment the method spans.
    - **Writers never lock:** inner nodes are published by a CAS from null, leaf slots are swapped by CAS, and clearing is a CAS from the method to null. Overlapping inserts can only be duplicates, e.g. `GenerateEvents` racing a live event; the record at the lower address wins and the other retires itself.
    - **Reclamation is epoch-based:** readers (the signal handler, enumeration, inserting threads) hold a `ReadGuard`. Whoever wins `CompiledMethod::retire()`, a CAS of `state` from LIVE to RETIRED, unlinks the record, then `synchronize()` advances the epoch and waits for readers of the previous one before returning the block to the arena. Never call `insert`/`remove`/`synchronize` while holding a `ReadGuard`, or they deadlock.
    - **Counts:** each record holds a total `count` and a dense `pc_counts` array of saturating `atomic<uint16_t>`, one per possible instruction start, covering `[code_begin, code_begin + (profile_length << PC_SHIFT))`: the instructions plus the stubs after them. `PC_SHIFT` is 2 on AArch64, where instructions are 4 bytes and 4-byte aligned, and 0 elsewhere, since x86 lengths vary. The handler updates both through `CompiledMethod::record_sample`, indexing by `(pc - code_begin) >> PC_SHIFT`. The shift is stored in each record's header byte 47 (`pc_shift`). Java's `InstructionProfile` keeps byte-offset semantics: `count(offset)` returns 0 for unaligned offsets, `profileLength()` is bytes covered, `bytesPerCount()` gives the stride, and `counts()` is one entry per counter. Counters saturate at 65535, about 11 minutes of samples at one PC, so continuous profiling should call `Sampler.resetCounts()` well within that; it zeroes the kind, method and per-PC counts.
  - **Records live in the ProfileArena, which Java reads in place.**
    - **The arena** (`profile_arena.h/.cpp`) is a single region reserved with `mmap`, 512 MiB >> `PC_SHIFT` (128 MiB on AArch64); pages are committed only when touched. Inside the library, `Sampler` holds one read-only, native-order view of it as a `ByteBuffer`. Users never see the buffer or how much of it is used.
    - **Public API:** `Sampler.forEachMethod(Consumer<InstructionProfile>)` walks the blocks by `blockLength` and passes one reused flyweight per LIVE record. There is no stored block length: both lengths share one atomically written word at offset 0, and the block length is `CompiledMethod::block_size(profile_length, name_length)`, the padded record rounded to its size class. Java must compute it identically (`InstructionProfile.blockLength(int)`), or the walk derails. The consumer owns the flyweight, and any `counts()` view taken from it, only until `accept` returns. Anything kept must be `snapshot()`, a frozen heap copy. `snapshot()` compares the generation recorded when the flyweight was positioned and throws `ConcurrentModificationException` if the block was reused for another method. The flyweight's positioning internals (`wrap`, `blockLength`, `generation`, `isStable`, the constructor) are package-private.
    - **Top-k selection:** `Sampler.forEachHottestMethod(k, consumer)` makes one pass with the flyweight, keeping a bounded min-heap (`TopK`) on parallel primitive arrays of (total, record position, generation). That is O(n log k) with no allocation per record. It then heapsorts those arrays in place into descending order and passes the flyweight, repositioned on each winner, to the consumer, with the same ownership as `forEachMethod`. A winner whose generation changed since selection (its block was reused) is skipped. Order is by the totals seen during the pass.
    - **Machine code on demand:** `InstructionProfile.machineCode()` calls `private static native machineCode0(address, methodSize, compileId)`. It is declared on `InstructionProfile` so nothing else can reach it, and takes primitives only, to keep the call cheap.
      - **Lookup:** natively it finds the blob with `CodeCache::lookup`, outside the signal handler, and reads its code section with `CodeCache::code_range` (`_code_offset`..`_data_offset` on JDK 23+, `_code_begin`..`_code_end` before). That span is exactly JVMTI's `code_size`.
      - **Exact match:** it copies only if the blob is an nmethod with the same compile id, code starting at `address` and `methodSize` bytes (after the same u16 saturation). The check is repeated after copying, and anything else returns null.
      - **Indexing:** the returned bytes are indexed like `counts()`.
    - **Formatter:** `InstructionProfileFormatter.format(profile, out)` prints the name, tier, compile id, then one row per sampled PC: `address + offset`, the instruction's bytes, its disassembly (with a direct branch inside the method annotated by the target's offset, `<+0xd0>`), the count and its share of `total()`. `allInstructions()` lists the whole method instead. Decoding uses a `parse` `Disassembler`, by default the one for the JVM's architecture (`forArchitecture`): `Aarch64Disassembler` on aarch64, `X86Disassembler` on amd64/x86_64. With no disassembler it shows bytes only, up to the next sampled PC and capped at 15. This is why `agent`'s `jvm` source set depends on `:parse`; the dependency is also declared on the `agentJar` configuration so consumers get it, and `agent-test`'s own `-javaagent` configuration is non-transitive.
    - **What the flyweight provides:** it is the only Java API for per-method data, names included, so anything Java needs about a compiled method must be in the record. `counts()` is a `CharBuffer` view of the per-PC counters: live for a consumer's flyweight, the copy for a snapshot. `name()`/`appendName()` decode the name, which JVMTI reports as modified UTF-8: one, two or three bytes per char, with supplementary characters stored as surrogate pairs.
    - **Block layout:** each block is a `CompiledMethod` (`compiled_method.h`): a 48-byte header, then the counts, then the name. `profile_length`, `name_length` and `code_size` are `u16`: an nmethod is mapped and profiled for at most 64 KiB from `code_begin`, with samples beyond that counted as stubs. `comp_level` is an `i8`. `state` stays a 32-bit word because it is CASed. The layout is defined in two places that must match exactly: the struct, guarded by `static_assert`s on every offset, and the constants in `InstructionProfile`. Native-only fields (`header_offset`, which locates the nmethod start before `code_begin`, and the `jmethodID` matched against `CompiledMethodUnload`) are part of the shared layout. The mapped range is not stored but derived: `[code_begin - header_offset, code_begin + profile_length)`.
    - **Allocation:** blocks are carved by bumping `used`, and each block's lengths word is written before `used` is published, so Java's walk never derives a wrong length for a fresh block. Sizes are rounded to four size classes per power of two. A freed block (after `synchronize()`) goes on its class's free list and is only reused for a record of the same class, so its derived length never changes, even for a reader racing the reuse. Churn therefore reuses space instead of growing the arena.
    - **Detecting reuse:** `generation` is odd while a block is being (re)initialised, and `state` goes FREE → LIVE (inserted) → RETIRED (being unlinked) → FREE (reclaimed). The flyweight reads both with acquire semantics (a VarHandle); `snapshot()` relies on them.
    - **Ownership:** the map never frees records itself; the arena outlives it. Unmapping the arena on library unload invalidates any `ByteBuffer` Java still holds.
  - **VMStructs** (`vm_structs.h/.cpp`) reads the `gHotSpotVM*` tables, finding libjvm with `dladdr` on a JNI function. Its format is unspecified and entries change between JDK versions, so:
    - Look fields up by name. Use `first_field` with the alternative type names a field has had (e.g. `nmethod`/`CompiledMethod._method`, `GrowableArrayBase`/`GenericGrowableArray._len`).
    - Read each field at the width of its declared type, taken from VMTypes. `CompLevel` is 1 byte on JDK 25 and an `int` on JDK 17.
    - Treat any missing entry as "layout unavailable", which makes every sample `UNKNOWN`. Don't guess offsets.
    - On macOS, JDKs before 25 don't export the `gHotSpot*` symbols. They are present only in the local symbol table.
  - **CodeCache::lookup** works in this order:
    1. Outside `CodeCache::_low_bound/_high_bound`: `NATIVE`.
    2. Inside the `AbstractInterpreter::_code` StubQueue: `INTERPRETED`.
    3. Otherwise, find the blob with each CodeHeap's segment map, as HotSpot's `CodeHeap::find_start` does, and validate it against the `HeapBlock` used flag and `CodeBlob._size`.
    4. A blob is an nmethod (`COMPILED`) if `CodeBlob._kind == CodeBlobKind::Nmethod` (JDK 23+) or, on earlier JDKs, if its `_name` is `"nmethod"`. Any other blob is `STUB`.
  - **Native linking and exports:**
    - **Linux:** the library links the C++ runtime statically (`-static-libstdc++ -static-libgcc`), so it only needs libc and the dynamic loader. `-Wl,--exclude-libs,ALL` keeps the runtime's symbols out of the dynamic symbol table, and `agent/src/main/linker/exports.map` (`--version-script`) exports only `Java_*`/`JNI_*`. The version script is needed because libstdc++ gives `std` templates instantiated in our code default visibility.
    - **All platforms:** code is compiled with `-fvisibility=hidden -fvisibility-inlines-hidden`, so only `JNIEXPORT` functions are exported. A new native entry point must be `JNIEXPORT` and named `Java_*` or `JNI_*`.
  - On macOS the build adds the SDK's libc++ headers (`xcrun --show-sdk-path`) because Gradle looks for them in a Command Line Tools directory that recent versions no longer have.
  - **Platform directory names:** `<os>` is one of `linux` (glibc), `linux-musl` (musl, detected by `/lib/ld-musl-*` at build time and at load time), `macos` or `windows`, and `<arch>` is `x86_64` or `aarch64` (e.g. `linux-musl-aarch64`). The OS is part of the path so `.so` and `.dylib` builds for the same architecture stay apart, a glibc build is never loaded on musl, and native initialisation dispatches on the current OS. The mapping exists twice and must stay in sync: `normaliseOperatingSystem`/`normaliseArchitecture` in `agent/build.gradle.kts` and `NativeLibraryLoader.platform()`.
  - Multi-architecture builds: a matrix job per OS/architecture builds and tests, then publishes `agent/build/native-libs`. A final job merges them with `-Pinstructive.nativeLibs`. Where the same file comes from more than one source, the locally built library wins.
- **parse** — plain Java analysis code, tested with JUnit 6.
  - **Disassembler API:** `Disassembler` (decode one instruction at an offset, or a whole method) returns `Instruction` records: address, length, mnemonic, operands, `InstructionKind` (branch/call/return variants, ALU, load, store, atomic, FP, SIMD, system...) and any direct branch target. Bytes a decoder can't decode come back as `.word`/`.byte` with kind `UNKNOWN` (`isDecoded()` is false).
  - **`aarch64.Aarch64Disassembler`:** decodes the A64 instructions JIT compilers emit: integer ALU, bitfield, moves, loads/stores (pairs, exclusives, acquire/release, LSE atomics), branches, barriers, hints, system registers and scalar FP. Vector SIMD is only classified, as `SIMD`, and comes back as `.word 0x...`, like anything else it can't decode.
  - **Text format:** follows `llvm-objdump` exactly so the two can be compared. That means LLVM's alias choices (for example, `orr` with the zero register is shown as `mov` only when `movz`/`movn` can't produce the value), hex immediates except shift amounts and bitfield positions, and absolute branch targets.
  - **Verification:** on 525k instructions of HotSpot-compiled code it matched `llvm-objdump` on every instruction it decoded, and on 2M random words it never claimed an encoding LLVM disagreed with. The only differences were system-register and `sys` alias names LLVM knows, which are printed in generic `S3_...`/`sys` form.
  - **Test vectors:** `src/test/resources/instructive/parse/aarch64/llvm-vectors.tsv` holds about 5,000 of those (address, word, LLVM text) cases, up to eight per instruction shape, and `undecodable.txt` lists words LLVM rejects. They were regenerated by assembling `.word` lists with `clang` and disassembling with `llvm-objdump`. When changing the decoder, keep it matching both files.
- **analyse** — plain Java analysis of decoded machine code, built on `parse` (an `api` dependency, so `parse`'s types are part of its API). Tested with JUnit 6, on JDK 25 in CI.
  - **`ControlFlowGraph`:** basic blocks, with leaders at the entry, in-method branch targets and after branches. Conditional branches have two successors, `b` one; returns, indirect branches, traps and undecodable words end paths; calls fall through. Also reverse postorder, dominators (Cooper/Harvey/Kennedy) and natural loops of back-edges, with the innermost loop per block. Unreachable blocks are extra roots, since nmethod stubs and handlers are entered from outside.
  - **`DependencyGraph`:** control-flow aware, built on reaching definitions per register. An undecoded instruction kills every definition.
    - **Two passes:** reaching definitions are computed on the full graph and again without retreating edges. Writes that reach only round a back-edge are loop-carried (`loopCarriedDependencies`); the rest are within one iteration (`dependencies`).
    - **Straight-line chains** (`chainLength`/`longestChainEndingAt`) follow within-iteration dependencies only between instructions in the same innermost loop, so they don't stitch together pre-loop, loop body and tail.
    - **Recurrences** (`recurrences()`): for each loop-carried dependency of `u` on `d`, the longest within-iteration path from `u` to `d` inside their smallest common loop. That is the cycle each iteration must execute serially.
  - **`LongDependencyChainRule`:** reports `LOOP_CARRIED` recurrences whose critical path (the cycle) is at least 8 instructions, keeping the longest of overlapping ones, and `STRAIGHT_LINE` chains of at least 16 that aren't contained in a reported recurrence.
    - **A recurrence's `instructions`:** `DependencyGraph.dependenciesWithin(producer, loop)`, a backward walk from the instruction producing the carried value through the writers of every operand within the iteration, so loads and address arithmetic are included, plus `DependencyGraph.storesOf(chain, loop)`: stores whose *stored* register (`RegisterUsage.stored`, the data operand, not the address) was written by the chain within the iteration. `criticalPath` is the cycle itself, and `samples` covers all of `instructions`, so samples attributed to a chain's loads count towards it.
    - **Ranking:** findings are ranked by `samples`, then critical path. `spanSamples` stays as context: the whole loop for a recurrence, the address range for a straight-line chain.
  - **Register usage** comes from `parse`'s `RegisterModel`/`RegisterUsage`. `Aarch64RegisterModel` derives it from the decoded mnemonic and operands: canonical names `x0..x30`/`sp`/`v0..v31`, the zero register dropped, condition flags not modelled. `stored` separates a store's data registers from its address registers.
  - **End to end:** `agent-test`'s `DependencyChainTest` runs `Arrays.hashCode(int[])` with `-XX:-UseVectorizedHashCodeIntrinsic`, because otherwise JDK 25 on AArch64 calls a SIMD stub that isn't tracked. It expects a loop-carried recurrence made of `lsl #5`/`sub`/`add`. It is AArch64-only because only `Aarch64RegisterModel` exists so far.
  - **`x86.X86Disassembler`:** decodes x86-64 in 64-bit mode, in LLVM's Intel syntax (`llvm-objdump -M intel`): `qword ptr [rbx + 8*rcx - 0x10]`, `riz` for an empty SIB index, imm8 printed signed, `{k1} {z}`, `{1to16}`, `{rn-sae}`, absolute branch targets.
    - **Two halves:** general purpose instructions (one-byte and 0F maps, groups, string ops, system instructions) and x87 are decoded by hand from compact specs (`op("mov Ev,Gv", ...)`). SSE, AVX, AVX-512, AMX, BMI, SHA, AES, GFNI... (legacy 0F/0F38/0F3A, VEX and EVEX) are looked up in `OpcodeTable`, loaded from `src/main/resources/instructive/parse/x86/opcodes.txt`. That file is generated by `parse/tools/x86/opcodes.py`, which probes LLVM's disassembler with every encoding and records each operand's source field, class per vector length, masking/broadcast/rounding forms, the EVEX disp8×N scale and immediates folded into mnemonics (`cmpeqps`, `vpcmpltud`). Don't edit it by hand; see `parse/tools/x86/README.md`.
    - **Matching LLVM's quirks:** LLVM's printing depends on prefix placement. A 66/F2/F3 is "mandatory" when it sits right before 0F (or REX, or for F2/F3 before 66). In the 0F maps a mandatory prefix suppresses `lock`/`rep` printing; elsewhere `rep`/`repne` are printed on any instruction; `addr32` is printed when a 67 prefix affects nothing. These rules are encoded in `Decoding.finish` and the prefix loop.
    - **Deliberate differences:** a leading `lock` is merged into the following instruction (`lock cmpxchg ...`; LLVM prints it as an instruction of its own) because a sample can never land between them. A lone prefix decodes as `.byte`. LLVM prints an F2/F3 before `lock`, `xchg` (or F3 before `mov` to memory) as a separate `xacquire`/`xrelease`; here it stays a `repne`/`rep` on the instruction, and the vectors don't cover those cases. APX (REX2 and extended EVEX), XOP, 3DNow! and VIA PadLock aren't decoded.
    - **Verification:** it matched LLVM on all 7.37M instructions of HotSpot-compiled x86-64 code collected under 12 flag combinations (apart from 25 APX-looking data bytes), on an exhaustive sweep of the one-byte and 0F maps (1.8M encodings), on random encodings (6M) and on random encodings of every table entry (480k). What remains are about 60 per million random encodings with unusual prefix combinations (66 or 67 before REX in the 0F maps, F3 away from the opcode), which compilers don't emit.
    - **Test vectors:** `src/test/resources/instructive/parse/x86/llvm-vectors.tsv` holds about 33,000 (address, bytes, LLVM text) cases, one per instruction shape (mnemonic, encoding, operand kinds) across those sources and three per shape from HotSpot code; `undecodable.txt` holds 3,000 encodings LLVM rejects. When changing the decoder, keep it matching both files.
- **agent-test** — JUnit 5 integration tests that depend on `agent` and `parse`. The test JVM is started with `-javaagent:` pointing at the agent jar plus `--enable-native-access=ALL-UNNAMED`, which JDK 24+ needs before `System.load` will run without a warning. The `Enable-Native-Access` manifest attribute does not cover `-javaagent`.

## Domain notes

These points hold for any JVMTI-based code capture and cut across the agent and the tools:

- **Code capture:** JIT-compiled methods arrive through the `CompiledMethodLoad` event, which carries the code address, the size and an address-to-bytecode-location map. Stubs and other VM-generated code arrive through `DynamicCodeGenerated`. Methods compiled before the agent attached are replayed by calling `GenerateEvents`.
- **Code lifetime:** compiled code is freed when `CompiledMethodUnload` fires, and its address range can then be reused by different code. Map each PC sample to the code blob that was live at the sample's time, not just to whatever blob covers that address range.
- **Copy bytes eagerly:** copy the code bytes during the load event, because the code may move or be freed later. Keep the agent's work inside events and signal handlers small and async-signal-safe, and leave decoding and analysis to the offline tools.
